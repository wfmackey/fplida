# fplida variable-fidelity upgrade — implementation plan

_Generated from the research-gap analysis workflow (12 domain analysts + 2 architecture analysts + synthesis). Source research: `inst/internal-docs/`._

## Executive summary

This is a large, multi-domain variable-fidelity upgrade touching every generator plus the spine and build harness, but the work decomposes cleanly because all generators are pull-based on spine columns and most fixes are cheap at the hot-loop level (one weighted_sample over a static const table). The dominant principle is to build shared infrastructure first: a canonical code-frame module (state, SACC country, ANZSCO, visa subclass, ASGS geography from the new mb_lookup.csv.gz), new spine columns (sa2/geography hierarchy, household/family id, latent SACC country-of-birth for the overseas-born, latent health propensities), a centralised seed-offset table, and a reconstructed deterministic schema-register builder that lets us measure progress at all. The current state is uneven: Census, BLADE, STP and PIT are column-name-faithful and need code-frame and reconciliation fixes; Home Affairs, NDIS, DSS/DEX, AEDC and Vital Events are compact stubs that need structural rebuilds (normalised multi-table products, missing tables, wide schemas). The single highest-impact cross-cutting change is fixing the country-of-birth semantics collision (a 0/1 flag emitted under names reserved for SACC codes corrupts cross-dataset joins) and the inconsistent STATE representation. Effort is concentrated in three structural rebuilds (Census household/family assembly, the BLADE R-to-Rust port, and the Home Affairs/NDIS/DEX/MCD/DEATHS multi-table reshapes), each Large. Many domain fixes are Small once the cross-cutting tables exist. Scope must stay disciplined: the research proves dataset scope and broad concepts almost everywhere but leaves exact code labels, distributions and cutoffs underspecified for most non-Census/non-BLADE datasets, so those stay labelled synthetic rather than invented. PIT/STP compactness is by design and its omitted DIL items are deferrals, not gaps. The plan sequences cross-cutting work first, then P0 correctness fixes (wrong code frames, degenerate constants, broken date ordering), then P1 structural rebuilds, then P2/P3 enrichment, validating continuously against the regenerated schema register and per-change testthat + cargo tests.

## Guiding principles

- Rust-first, always: all generation logic lives in Rust; R wrappers only load spine columns, call the extendr function, write parquet, and return metadata. No new generation logic in R (this also reverses the BLADE anomaly where 2,372 lines of value logic live in R/generate_blade.R).
- Code frames are authoritative, distributions are synthetic: where a source code frame exists (Census Dictionary mnemonics, BLADE/STP/PIT DIL names, AVETMISS state codes, TCSI E329/E330, PBS benefit_type U/R/A/S, DRG co-payments), match it exactly; where only the concept is sourced, keep generated frequencies/labels explicitly labelled local/synthetic and never promote a sampled value to a source fact.
- Never invent fidelity the sources don't support: the research grades most non-Census/non-BLADE value domains as underspecified. Underspecified means keep-as-synthetic, not free-to-fabricate. Do not fill a documented evidence gap (visa/traveller codebooks, AEDC cutoffs, apprentice weights, UCOD distributions) with invented detail.
- Compact-by-design is not a gap: PIT_PS (14 of ~40 DIL items) and PIT_ITR (~23 of 601) and STP Phase-1 columns are intentionally compact; their omitted DIL items are deferrals. Only the few explicitly-wrong items (PIT_IE reconciliation, naming crosswalks, year-key mismatch) are in scope unless a DIL-shaped surface is explicitly chosen.
- Hot-loop discipline at 10M scale: every per-row change must be a const-table lookup or one extra weighted_sample/RNG draw with zero new allocation; push u8/i32 codes or &'static str into chunk buffers and resolve labels at batch time; never push owned per-row Strings in the MBS/PBS/STP hot loops; use Col::I32Opt/StrOpt/Date for nullable columns and a constant-column parquet encoding for the many always-zero STP fields.
- Shared infrastructure before per-domain work: a single canonical code-frame module and shared spine columns (geography, household id, SACC country, latent health) unblock many domains at once and enforce cross-dataset consistency, so they are built first.
- Reproducibility is sacred: add new spine attributes via a fresh sub-RNG at base_seed+6 placed after dependencies; centralise the seed-offset map so new generators cannot silently correlate; bump the spine-template version constant whenever spine columns change so stale ~100k templates rebuild.
- Measurement before progress: the schema-register builder must be reconstructed and committed first, because without a deterministic regeneration of generated-schema-register.csv there is no automated way to measure whether fidelity improved or regressed.
- Edit both spine emitters in lockstep: any spine column change must touch the Person struct, the setting sub-module, AND both to_r_list and persons_to_arrays, or the default template path and the legacy path diverge.
- Preserve the four-layer reconciliation separation: DIL metadata surface vs current generated output vs official source coverage vs unresolved gaps. Do not merge these into one data dictionary that reads as if synthetic values are source facts.

## Cross-cutting infrastructure (build first)

### [M] codeframes.rs: canonical shared code-frame module
- **Why:** Eliminates the four cross-dataset inconsistencies the reconciliation registers expose (STATE three ways, country-of-birth name/semantics collision, mixed ANZSCO levels/NA sentinels, ununified visa subclass). Holds const SACC country table + weighted sampler, AVETMISS state 01-08/09/99 map, ASGS state->SA2/SA3/SA4/LGA/MB lookup loaded once from inst/extdata/mb_lookup.csv.gz, canonical ANZSCO NA handling, and one visa-subclass code+label list. Every per-row use is an O(1)/O(k) const lookup with no allocation.
- **Affects:** Census, Health(AIR), DSS, NDIS, Home Affairs, Vital Events, Education, VET, CORE

### [L] Spine geography hierarchy column(s) (sa2_code derived consistently with state, via mb_lookup)
- **Why:** Census, CORE-locations, DOMINO, NDIS, Home Affairs, Vital Events all independently invent or omit sub-state geography; a single spine geography column shared via load_spine_select makes person and dwelling geography consistent and is free to generators that ignore it. Add via a new spine sub-module + sub-RNG at base_seed+6 after demographics; emit in both to_r_list and persons_to_arrays; bump template version.
- **Affects:** Census, CORE, DOMINO, NDIS, Home Affairs(MT_DEMOGS/SDB), Vital Events(BIRTHS/DEATHS/MCD), Education(AEDC)

### [L] Spine household/family id column
- **Why:** Census household/family assembly, CORE relationships, and DOMINO all re-derive households independently and inconsistently. Assigning a stable household/family id on the spine (single bucketed pass respecting age gaps and marital status) lets Census derive DWELLING_ID/FAMILY_ID/RLHP and CORE relationships reuse it, avoiding O(n^2) and divergence. This is the enabler for the highest-effort Census change.
- **Affects:** Census (DWELLING_ID/FAMILY_ID/RLHP/FPIP/SPIP), CORE relationships, DOMINO principal-carer

### [M] Spine latent SACC country-of-birth code for overseas-born
- **Why:** Root-cause fix for the constant-1 country-of-birth defect across SDB/VISA/MT_DEMOGS/DEX/DOMINO/A&T and the binary-vs-SACC name collision. Enriching demographics.rs to carry a real SACC code (passed through unchanged) fixes all Home Affairs, DSS, NDIS-CALD, Census BPLP and HE COUNTRY_BIRTH at once; reserve *_CTRY_CODE/country-of-birth names for the code and rename 0/1 flags to BORN_IN_AUSTRALIA_FLAG.
- **Affects:** Home Affairs, DSS, NDIS, Census, HE, DOMINO, A&T

### [M] Spine latent health/condition propensities beyond person_type
- **Why:** Keeps Census health flags (HLTHP/HOLHP/COxxxP), MBS, PBS, SDAC and DOMINO disability payments mutually consistent for the same individual; without it each dataset draws conditions independently. Lower priority than geography/household but high value for health-shock cross-dataset coherence.
- **Affects:** Census(health), Health(MBS/PBS), DSS(DOMINO medical), CORE/SDAC, NDIS

### [S] seeds.rs: centralised seed-offset table
- **Why:** The offset map is currently an implicit convention across 58 wrapping_add sites plus the per-slice +slice_id*100000 spacing; two generators sharing an offset silently correlate. A const table makes adding generators (NDIS products, DEX tables, death_registrations, BLADE) safe.
- **Affects:** all generators

### [M] Reconstructed deterministic schema-register builder + committed re-validation diff pipeline
- **Why:** No committed script regenerates generated-schema-register.csv (it came from an ad-hoc live run incl. a one-off /tmp PIT FY2021 build), so progress is unmeasurable. Build a fixed-seed dataset, read every parquet, record per-column type/missingness/distinct/domain, left-join PLIDA+BLADE metadata, force a non-empty PIT FY2021 run; then a diff pipeline that asserts variable sets preserved/grown, the 4 not-source-equivalent rows unchanged, and observed_in_generated_register coverage non-decreasing. Must exist before measuring any fidelity gain.
- **Affects:** all domains (measurement)

### [S] parquet_io.rs constant-column encoding (Col::F64Const/I32Const)
- **Why:** STP materialises ~25 always-zero extended columns as full vec![0.0; n_rows] per chunk; at 10M this is large transient allocation. A constant-column variant cuts memory/allocation for the many fields the research mandates stay zero, and is reusable by NDIS/DEX null-heavy columns.
- **Affects:** STP, NDIS, DEX, Vital Events

### [S] Foundation-TOML drift guard (or include_str! single-source-of-truth)
- **Why:** TOMLs are documentation-only and hand-transcribed to Rust consts with no link, so calibration silently drifts. Either add a testthat test that re-parses each TOML and asserts consts match, or switch to include_str!+once_cell. New foundation tables (pit_ie.toml, dex.toml, aedc.toml, deaths cause-distribution, air.toml) make this more pressing. Make the choice deliberately.
- **Affects:** all calibrated generators

## Workstreams (by priority)

### P0 — Cross-cutting foundation (code frames, spine columns, seeds, schema-register builder)  _(effort XL)_
**Headline gaps:**
- No shared code-frame module: STATE emitted three ways (ASGS 1-8 numeric, DOMINO/NACDC abbreviations, DEATHS float, NDIS truncated 1-4); country-of-birth name collision (SACC code vs 0/1 flag under COUNTRY_OF_BIRTH in NACDC/DEX/A&T/DOMINO-BIRTH_CTRY_CODE); ANZSCO at mixed levels with mixed NA sentinels; visa subclass not unified between SDB and VISA.
- Spine lacks geography below state, household/family id, latent SACC country-of-birth for overseas-born (collapses to constant 1), and latent health propensities beyond person_type, forcing every downstream dataset to independently invent these.
- Foundation TOMLs are documentation-only (no runtime load); numbers hand-transcribed into Rust consts with no drift guard.
- Seed-offset map is an implicit hand-maintained convention scattered across 58 wrapping_add sites; collision risk when adding generators.
- No committed builder regenerates generated-schema-register.csv; progress is unmeasurable.

**Rust targets:** new src/rust/src/codeframes.rs (const SACC country table + weighted sampler, AVETMISS state 01-08/09/99 map, canonical ANZSCO NA handling, visa-subclass code+label list, ASGS state->SA2/SA3/SA4/LGA/MB lookup loaded once from mb_lookup.csv.gz); new src/rust/src/seeds.rs (central const offset table); src/rust/src/spine/mod.rs Person struct + to_r_list; src/rust/src/spine_template.rs persons_to_arrays; new spine sub-module (geography.rs) + sub-RNG at base_seed+6; extend demographics.rs to emit a real SACC country_of_birth_code for overseas-born; optional: toml-parsing once_cell statics or a testthat drift-check instead of include_str!

### P2 — Core spine demographics, COMBINED, ACLD, SDAC  _(effort M)_
**Headline gaps:**

**Rust targets:** src/rust/src/core_gen.rs::project_core_relationships__ (no self-link guard; sex/age-compatible partners; capped children-per-parent via draw-without-replacement; REL_CODE; varied SOURCE_FLAG); src/rust/src/core_gen.rs::project_core_demographics__ (year-by-year survival hazard for death year); src/rust/src/core_gen.rs::project_core_locations__ (SA3/LGA from extended lookup; CONFLICT_FLAG/treat-flags; weighted SOURCE_FLAG/ADR_TYP); src/rust/src/sdac.rs (unambiguous NA sentinel for DISGP/DISTYPE); optional acld.toml/sdac.toml externalising code frames; optional spine indigenous code-9 share

## Risks

- Scope creep into inventing unsourced fidelity: the research grades most non-Census/non-BLADE value domains as underspecified, which means keep-as-synthetic, not free-to-fabricate. The biggest risk is a contributor 'cleaning up' a degenerate column (visa subclass labels, AEDC cutoffs, UCOD distributions, apprentice weights) with plausible-but-invented codes, regressing the audit. Mitigate by gating any code-frame change on a confirmed source and labelling everything else synthetic.
- Spine emitter divergence: the Person struct, to_r_list, and persons_to_arrays must change in lockstep, and the template path (default) is what build_fplida actually uses. Forgetting persons_to_arrays or the template-version bump silently ships a stale ~100k template missing the new columns. Mitigate with a test asserting both emitters produce identical schemas.
- Cross-person datasets cannot be sliced: Census household assembly and CORE relationships need all N at once and must run centrally before PSOCK workers. Putting household logic in a sliced worker would break consistency at slice boundaries. The spine household-id approach sidesteps this only if the id is assigned centrally in the spine build.
- Several decisions are owner-gated and block their workstreams: full-detail vs collapsed Census large classifications; TRAVELLERS wide (~300 cols, large build cost) vs compact; whether PIT/STP go DIL-shaped; whether MCD belongs in vital-events; BLADE longitudinal vs snapshot and which of tables 8-62 to fully model. Surface these early so they don't stall Phase 4.
- Unverified value domains needed before some 'fixes': STP ETP/lump-sum codes, DEX EXITREASONCODE, NDIS/DOMINO disability-group labels, AVETMISS state ordering vs spine state ordering. Changing these before confirming the source set risks shipping a different-but-still-wrong frame. Confirm from the DIL spreadsheets/protocol PDFs first.
- 10M-scale regressions from naive additions: BLADE per-row regex, STP always-zero column allocations, HE in-loop institution-candidate Vec rebuild, MBS per-chunk postcode_strings rebuild, and travellers per-row String building are existing hot-loop hazards that get worse if extended carelessly. Mitigate by const-table dispatch, constant-column encoding, and hoisting precomputed lookups out of loops; benchmark at 1M before and after each structural change.
- ICD-10 / ASGS lookup data dependencies: DEATHS UCOD validation needs an ICD-10 valid-code list and the births/deaths/MCD geography needs mb_lookup to actually carry SA3/LGA/PHN/IREG, which is unconfirmed. If mb_lookup only has mesh-block->SA hierarchy, LGA/PHN/IREG must be sourced separately or those columns stay null.
- Measurement baseline fragility: the schema register was produced by an ad-hoc run, so the reconstructed builder may not reproduce the exact 1,585-row baseline (especially the one-off PIT path). Treat the first regeneration as establishing a new committed baseline rather than expecting byte-identical reproduction.

## Validation strategy

Run validation at three levels on every change. (1) Reconciliation level: regenerate generated-schema-register.csv with the reconstructed deterministic builder (fixed seed, all parquet read, PLIDA+BLADE metadata joins, forced non-empty PIT FY2021 run), then diff per-guide variable sets against the committed baseline to confirm no variables dropped/renamed unintentionally and counts hold or grow; re-run build-variable-code-evidence-registers.R and assert the four explicitly not-source-equivalent rows (PIT_PS SUPER_GUARANTEE/UNION_FEES/WORKPLACE_GIVING, NACDC INDIGENOUS_STATUS) plus the dhda value-domain flags are unchanged; recompute observed_in_generated_register over the 49,987-row inventory and require it be non-decreasing (coverage as the headline progress metric). The Use Rule is a hard gate: fail the build if any change promotes a sampled value to a source fact. (2) Per-change R level: extend the existing testthat suites (test-generate_census.R, test-generate_core.R, test-build_csv.R, test-dil-2026.R, test-generate_blade.R) with assertions for each new/changed column — code-frame membership (regex against the official set), domain non-degeneracy (distinct>1 where a constant was a defect), relationship invariants (Census FMCF/CPRF consistent with assembled membership; SDB DATE_OF_GRANT vs ARRIVAL_DATE per the offshore/onshore design; PIT_IE TOTALINC == component sum pre-noise, NONLODGER='PS' iff absent from ITR, BAL == NET_TAX less PS withholding; STP INCM_GRS_AMT==PMT_SUMRY_TOTL_GRS_PMT_AMT and negative-correction rules; DEATHS RECORD_AXIS_COUNT == populated RACS slots; births REG_YEAR>=BIRTH_YEAR), and cross-dataset consistency (same individual resolves to the same STATE/country-of-birth/ANZSCO across Census/CORE/health/Home Affairs). (3) Rust level: cargo test for new const-table parsing, weighted samplers, the BLADE VariableSpec classifier, and the household/family assembly single-pass; cargo build under the rustup toolchain with $HOME/.cargo/bin on PATH; benchmark build_fplida at 1M before/after every structural change (BLADE port, Census assembly, NDIS/DEX/Vital-Events reshapes, travellers widening) to catch hot-loop regressions, comparing against the recorded 1M timings (mbs ~568s, pbs ~328s) so MBS/PBS dominance is not worsened. Regenerate R/extendr-wrappers.R and NAMESPACE via rextendr::document() after any new #[extendr] function and smoke-call it from R post-install.

# Appendix A — Architecture analyses

## fplida generation roots: spine, build controller, foundations, extendr wiring, and Rust column conventions

The fplida package generates synthetic PLIDA data from a single canonical "spine" (one row per person, 36 base columns + 13 agency AEUID columns) which every downstream generator consumes by selectively loading a subset of spine columns and projecting agency-specific tables. Generation is Rust-first: the spine is built in src/rust/src/spine/ (one sub-module per attribute block: demographics, education, occupation, income, linkage, disability), serialised to Arrow/parquet entirely in Rust, then sampled-with-replacement from a ~100k template for speed at large N. The build controller (R/build_fplida.R) runs spine + core + blade centrally, then slices the spine into K disjoint person ranges and runs all other generators in parallel PSOCK workers, merging part files at the end. The "foundations" TOML files in inst/foundations/ are documentation/provenance only — they are NOT parsed at runtime; their numbers are hand-transcribed into Rust `const` arrays. New Rust functions are exposed to R through extendr's `#[extendr]` + `extendr_module!` macros, but R/extendr-wrappers.R and NAMESPACE are NOT regenerated automatically here — they are committed artefacts that must be updated (by re-running `rextendr::document()` or manually). Nullable columns use Vec<Rint>/Vec<Rbool>/Vec<Rfloat> for the R-list path and Vec<Option<String>> / parquet_io::Col variants (I32Opt, StrOpt, Date) for the direct-parquet path. The recipe and gotchas for each of the four extension tasks are below.

**Findings:**
- **Spine columns produced (the canonical contract)** — The spine is defined by the `Person` struct at src/rust/src/spine/mod.rs:20-65 and emitted in two parallel code paths that MUST stay in lockstep: (a) `to_r_list` (mod.rs:161-320) builds an R `list!(...)` of 36 columns; (b) `persons_to_arrays` (spine_template.rs:60-277) builds the identical 36 columns as Arrow ArrayRefs for direct parquet. Column order/names: id, spine_id, birth_year, sex, state, indigenous, country_of_birth, year_of_arrival, citizenship, education, archetype, anzsco_code, anzsco_unit, anzsco_major, anzsco_title, skill_level, task_cognitive, task_physical, task_vision, task_hearing, task_manual_dexterity, task_communication, industry, sector, individual_fe, occ_match_quality, baseline_employed, baseline_hours, baseline_income, disability_onset_year, disability_type, disability_severity, is_dc, disability_dose, person_type, comorbidity_flags. `id`/`spine_id` are character 'P0000000001'/'SP0000000001'. ANZSCO fields are looked up positionally from anzsco_table::ANZSCO_CODES/ANZSCO_TITLES via the stored anzsco_index (mod.rs:224-237). After Rust returns, R appends 13 `aeuid_<agency>` columns (one per .AGENCIES entry) — so the on-disk base-spine.parquet has 36+13 = 49 columns.
  - _Implication:_ Any reimplementation must treat the Person struct + the TWO emitters (to_r_list and persons_to_arrays) as a single unit. Adding a spine column requires editing all of: struct field, the sub-module that sets it, AND both emitters, or the template path and the legacy path will diverge (the template path is the default and is what build_fplida actually uses).
- **How spine attributes are assigned (sub-module structure)** — build_persons (mod.rs:70-94) creates 6 independent sub-RNGs seeded base_seed+0..+5 (rng_demo, rng_edu, rng_occ, rng_inc, rng_link, rng_dis) and calls demographics::assign, education::assign, occupation::assign, income::assign, linkage::assign, assign_disability in sequence per person. The comment at mod.rs:73 is load-bearing: separate sub-RNGs exist 'so adding later steps doesn't change earlier outputs'. demographics.rs uses ABS-calibrated const weight arrays (age bands, sex, state, indigenous, COB, citizenship). education.rs has a cohort-conditioned 3x5 weight matrix. occupation.rs assigns one of 8 archetypes via a 5x8 education-archetype affinity matrix, then a random ANZSCO code within ARCHETYPE_RANGES[arch], jitters 6D task scores around archetype centres, and picks industry/sector. income.rs computes baseline_employed (age-conditional), individual_fe ~N(0,0.4), occ_match_quality, hours, and a log-normal baseline_income with occupation intercept MU_OCC + age profile + female penalty. linkage.rs currently just sets has_spine_link=true (agency linkage failure is applied later at write time, not here).
  - _Implication:_ To add a NEW spine attribute that depends on existing ones (e.g. an occupation-derived task index, a region/SA2, a wealth proxy), add a new sub-module + a new sub-RNG at base_seed+6 in build_persons AFTER the steps it depends on, set the field there, and emit it. Using a fresh +6 RNG (not reusing an existing one) preserves reproducibility of all existing columns.
- **NEW spine columns to support richer downstream variables** — Downstream generators are bottlenecked by what the spine carries. Today the spine has NO geography below state (no SA2/SA1/postcode/ASGS), no partner/household linkage (that is computed separately in core_gen.rs +700..+702 as a cross-person pass, not stored on the spine), no time-varying employment (employment.rs +300..+370 derives a panel on the fly from baseline_* fields), no wealth/assets, no detailed migration/visa history beyond year_of_arrival, and only a single 2021-anchored occupation (no occupation mobility). Census already strains against this: project_census_person__ (census_2021.rs:700-717) receives 16 spine columns and must invent marital status, language, health conditions etc. from age/occupation because the spine lacks them.
  - _Implication:_ For a large variable-fidelity reimplementation, the highest-leverage spine additions are: (1) a stable geography hierarchy column set (sa2_code at minimum, derived consistently with state) so Census/CORE-locations/DOMINO can share it; (2) a household/family id assigned on the spine rather than re-derived per dataset; (3) latent health/condition propensities beyond the current person_type so Census health flags, MBS, PBS and SDAC stay mutually consistent; (4) a wealth/assets latent for ITR/CGT/SMSF. Each new column is cheap to thread through because generators already do selective column loading — they only pay for columns they request.
- **How downstream generators consume the spine** — The universal pattern (see generate_census.R:44-66, generate_mbs.R:52-104): resolve_run_dir() finds the active run via the fplida.run_dir option; load_spine_select(run_dir, cols) reads ONLY the named columns from base-spine.parquet via arrow col_select (export.R:413-437); the R wrapper coerces those columns to plain atomic vectors and passes them positionally into a single #[extendr] Rust call; Rust does all per-person work and (for high-volume datasets) writes parquet itself; the wrapper writes the agency spine via write_agency_spine() and returns metadata. Each generator declares its own seed offset inside Rust (census +100, core +700/+701/+702, employment +300/+350/+360/+370, mbs participants +1000 / pools +1003 / per-chunk derived). The R wrapper passes the raw `seed`; the offset is added in Rust via `(seed as u64).wrapping_add(OFFSET)`.
  - _Implication:_ Adding a new generator or new emitted column never requires touching the spine writer — generators are pull-based on spine columns. But the seed-offset map is a hand-maintained convention spread across Rust files (grep `seed_from_u64` / `wrapping_add`), NOT a central table. A reimplementation should centralise these offsets (e.g. a `seeds.rs` consts module) to avoid collisions; today two generators using the same offset would silently correlate.
- **Build controller: order, central vs sliced, streaming, output layout** — build_fplida (R/build_fplida.R) canonical product order is the all_products vector at lines 162-169. Stages: (1) spine central, full N, return_data=FALSE writes _system/base-spine.parquet and sets options(fplida.run_dir) (lines 234-251); (2) core central if requested — cross-person partner/parent-child links (254-261); (2b) blade central — business source-of-truth (264-271); (3) materialise K slice spines via zero-copy Arrow $Slice into ephemeral temp run_dirs (slice_utils.R:54-125); (4) PSOCK cluster of K fresh R processes each running build_fplida_slice_worker (slice_worker.R) over worker_products = all minus spine/core/blade; (5) merge slice part files into canonical run_dir as {dataset}/{product}/part-NNN.parquet, agency spines concatenated via DuckDB (slice_utils.R:168-300); (6) cleanup; (7) L-drive strayr reference tables; (8) optional parquet→CSV via DuckDB. Per-slice seed = base_seed + slice_id*100000 (build_fplida.R:388). return_data=FALSE is the streaming contract: high-volume generators write parquet directly from Rust and return only counts/metadata, never materialising an R data.frame. Output folder: data_path/fplida_{Nk|Nm}[_suffix]/{_system, <agency>-<dataset>/...}. format_n rounds N (export.R:46-58); dataset_dir maps dataset->agency via .AGENCY_DATASETS (linkage.R:8-24).
  - _Implication:_ A new dataset must (a) be added to all_products in build_fplida.R, (b) be added to the .dispatch_slice_product switch in slice_worker.R (or to the central stages if it is cross-person like core/blade), and (c) have its dataset->agency mapping registered in .AGENCY_DATASETS. If the dataset is cross-person (needs all N at once, like partner matching) it CANNOT be sliced — it must run centrally before workers, because each slice worker only sees its own disjoint person range. The +slice_id*100000 offset bounds per-slice seed spacing; a generator that internally adds large offsets risks colliding across slices if its offsets approach 100000.
- **Foundations TOML mechanism (the key gotcha)** — inst/foundations/*.toml are NOT loaded or parsed at runtime by either R or Rust. Confirmed: grep for foundation/toml/include_str in src/rust/src finds only comments (mbs.rs:9 'Constants (from inst/foundations/mbs.toml)', pbs.rs:10, he.rs:9, census_2021.rs:8); grep in R finds only comments (census_projection.R:3, generate_core.R:130, generate_domino.R:187). There is no toml crate dependency, no include_str!, no read of these files. The TOML files are human-readable provenance/calibration registers; their numbers are hand-transcribed into Rust `const` arrays (e.g. demographics.rs AGE_BAND_WEIGHTS, core.toml mortality rates -> core_gen.rs consts, census_2021.toml -> census_2021.rs embedded distributions).
  - _Implication:_ 'Adding a foundation calibration table' today means TWO manual, decoupled steps: (1) document the numbers + sources in a new inst/foundations/<dataset>.toml for provenance; (2) transcribe them into Rust `const` arrays in the relevant generator module. There is no compile-time or runtime link between them, so they can silently drift. A higher-fidelity reimplementation could either (a) keep the manual convention but add a test that re-parses the TOML and asserts the Rust consts match, or (b) switch to compile-time embedding via `include_str!` + a toml parser in build.rs / a once_cell static, which would make the TOML the single source of truth. Either choice should be made deliberately; the current code assumes hand-sync.
- **extendr wiring: exposing a new Rust fn to R** — Three coordinated edits per new function: (1) annotate the Rust fn with #[extendr] and list it in that module's `extendr_module! { mod <name>; fn my_fn; }` block (e.g. combined.rs:97-101, spine/mod.rs:322-325, spine_template.rs:666-670); (2) ensure the module itself is declared `pub mod <name>;` in lib.rs:9-50 AND listed in the top-level `extendr_module! { mod fplida; use <name>; }` at lib.rs:59-101 — a module missing from this `use` list is invisible to R even if it compiles; (3) the R binding in R/extendr-wrappers.R (header says 'Generated by extendr: Do not edit by hand', wraps via `.Call(wrap__<fn>, args...)`, e.g. extendr-wrappers.R:50 generate_spine__) and the NAMESPACE `export(<fn>)` line. NAMESPACE currently has 94 `__` exports and `useDynLib(fplida, .registration = TRUE)` at line 159.
  - _Implication:_ Although extendr-wrappers.R is auto-generated by `rextendr::document()` (which regenerates the wrapper from `#[extendr]`/roxygen and rewrites NAMESPACE via roxygen2), in this repo both files are committed artefacts. The reliable recipe: after editing Rust, run the documentation step to regenerate wrappers + NAMESPACE, then `R CMD INSTALL .` with `$HOME/.cargo/bin` on PATH (per project memory). If regeneration is skipped, the function exists in the .so but has no R binding and no export — it is uncallable. Gotcha: forgetting the `use <name>;` line in lib.rs's top-level extendr_module! is the most common silent failure — the per-module extendr_module! is necessary but not sufficient.
- **Rust column conventions for emitting/nullable data** — Two emission paths with different nullable idioms. (A) R-list path (returns a List to R, used by census person, family, dwelling, combined::project_combined_indigenous__): non-null columns are plain Vec<i32>/Vec<f64>/Vec<bool>/Vec<String>; nullable columns use extendr's Vec<Rint>/Vec<Rfloat>/Vec<Rbool> pushing Rint::na() etc., and nullable strings use Vec<Option<String>> (mod.rs:165,178,195-201 and the corresponding na() pushes at 215-218, 254-279). (B) Direct-parquet path (parquet_io.rs Col enum, used by all high-volume generators): Col::I32/F64/Bool/Str for non-null; Col::I32Opt (i32::MIN sentinel = null, parquet_io.rs:63-69), Col::StrOpt (Vec<Option<String>>), Col::Date/DateNN (Date32, i32::MIN=null). Columns are wrapped in NamedCol{name, col} and passed to write_columns_to_parquet (combined.rs:74-92 is the canonical minimal example). parquet_io.rs auto-chunks at CHUNK_ROWS=1_000_000 and sets max_row_group_size=256_000 to stay under the Arrow 2GB i32-offset StringArray cap (a panic-level hazard at large N, build_fplida.R:355-368 explains the chunk-size budget). Code-frame lookups are positional const tables: ANZSCO via anzsco_index into ANZSCO_CODES/ANZSCO_TITLES; service profiles via service_profiles::PROFILES[(pt-1)]; all classification frames are Rust const arrays, not external files. Per project memory: Vec<Rint> not Vec<Robj>; Vec<Option<String>> not Vec<Rstr>; check is_na() on Strings because Rstr.to_string() on NA yields the literal 'NA'.
  - _Implication:_ To add/change an emitted column in a generator: in the R-list path add the Vec, the per-row push, and the list!() entry (3 sites); in the direct-parquet path add the Vec, the per-row push, and a NamedCol in the cols vec (3 sites). Pick the nullable variant matching the column's R type — I32Opt for nullable ints (NEVER plain i32, because i32::MIN would round-trip as a real value through the non-Opt path), StrOpt for nullable strings, Date for nullable dates. For string-heavy columns at large N, do not bypass write_columns_to_parquet's chunking, or risk the 2GB offset panic. If the column is a coded classification, add a const lookup table rather than mapping to an external framework (project rule: always use real PLIDA codes).

**Recommendations:**
- Recipe to ADD A SPINE COLUMN: (1) add the field to `Person` (src/rust/src/spine/mod.rs:20-65); (2) set it in the appropriate sub-module's assign() (or add a new sub-module + a new sub-RNG at base_seed+6 in build_persons, placed AFTER any steps it depends on, to preserve reproducibility of existing columns); (3) emit it in BOTH `to_r_list` (mod.rs:161-320: declare Vec, push per-row incl. NA path, add to list!()) AND `persons_to_arrays` (spine_template.rs:60-277: declare Vec, push, add to the vec! of (name, ArrayRef)) — these must match exactly or the template path (default) and legacy path diverge; (4) the template cache is keyed on seed + .SPINE_TEMPLATE_VERSION (spine_template.R:19) — bump that version constant so stale ~100k templates are rebuilt; (5) generators that need the new column add it to their load_spine_select() column list. Rebuild: `export PATH="$HOME/.cargo/bin:$PATH" && R CMD INSTALL .`.
- Recipe to ADD/CHANGE AN EMITTED COLUMN in a dataset generator: identify whether the generator returns an R List (census/combined style) or writes parquet directly (mbs/pbs/stp/employment/combined-to-parquet style). For the List path edit 3 sites (Vec decl, per-row push with correct Rint/Rfloat/Rbool/Option<String> NA handling, list!() entry). For the parquet path edit 3 sites (Vec decl, per-row push, NamedCol entry in the cols vec passed to write_columns_to_parquet). Choose the nullable Col variant by type: I32Opt (i32::MIN=null), StrOpt, Date — never plain i32 for a nullable int. Then update the empty-result helper (e.g. .empty_mbs_claims in generate_mbs.R:200) and any return_data read-back so schemas match.
- Recipe to ADD A NEW FOUNDATION CALIBRATION TABLE: be aware TOML is NOT runtime-loaded. (1) Create/extend inst/foundations/<dataset>.toml with the numbers, labels, and ABS/AIHW source citations for provenance; (2) hand-transcribe the values into Rust `const` arrays in the generator module (pattern: demographics.rs weight arrays, core_gen.rs from core.toml). Add a unit test asserting the transcribed consts match the TOML if drift is a concern. If the reimplementation wants the TOML as single source of truth, introduce a toml-parsing dependency + `include_str!` of the .toml into a once_cell static — but make that an explicit design decision, since it changes the current hand-sync contract.
- Recipe to EXPOSE A NEW RUST FN TO R: (1) annotate `#[extendr]` and add `fn my_fn;` to the module's local `extendr_module!` block; (2) confirm the module is both `pub mod <name>;` (lib.rs:9-50) and listed in the top-level `extendr_module! { mod fplida; use <name>; }` (lib.rs:59-101) — the `use` line is the easiest thing to forget and makes the fn invisible to R; (3) regenerate R bindings by running `rextendr::document()` (rewrites R/extendr-wrappers.R and the NAMESPACE export()s) rather than editing those by hand; (4) reinstall with cargo on PATH. Verify with a smoke call from R after install.
- For the variable-fidelity reimplementation, prioritise these spine additions because they unblock the most downstream fidelity at lowest cost: a shared geography hierarchy (sa2_code derived consistently with state), a spine-level household/family id (so Census, CORE-relationships and DOMINO stop independently re-deriving households), and latent health/condition propensities beyond person_type (so Census health flags, MBS, PBS, SDAC and DOMINO disability payments stay mutually consistent). Because generators pull only the columns they request via load_spine_select, new spine columns impose zero cost on generators that ignore them.
- Centralise the seed-offset map. It is currently an implicit, hand-maintained convention scattered across Rust modules (spine +0..+5, census +100, core +700..+702, employment +300..+370, mbs +1000/+1003, pbs +1100-range, etc.) plus the per-slice +slice_id*100000 spacing in build_fplida.R. A single `seeds.rs` consts module (or a documented table) would prevent silent cross-generator correlation and make it safe to add new generators without auditing every existing offset.

## fplida Reconciliation Framework: Support Verdicts, Re-validation, and Cross-Domain Code Frames

The owner built a four-layer reconciliation framework under inst/internal-docs/ to separate what fplida currently emits from what public/official sources actually prove. The layers are: (1) generated-schema-register.csv (1,585 generated-variable rows with observed type/missingness/domains, the empirical "what we emit today" baseline, split into 12 per-guide CSVs under schema-registers/); (2) generated-variable-crosswalk.csv (1,585 rows mapping each generated variable to local PLIDA/BLADE metadata with an evidence status); (3) local-metadata-variable-inventory.csv (49,987 rows = the full DIL surface, with an observed_in_generated_register flag that measures coverage); and (4) source-gap-register.csv (38 guide-level rows recording source_supports vs not_found_or_not_proven) plus seven stricter per-guide variable-code-evidence registers built by build-variable-code-evidence-registers.R. The governing rule (source-gap-register.qmd Use Rule; full-review.md P0 findings) is: never present sampled generated values as official source distributions, and never fill an evidence gap with invented detail. The research judged dataset SCOPE and broad CONCEPTS well-supported almost everywhere, but judged exact code labels, category domains, weights, distributions, and cutoffs UNDERSPECIFIED across most non-Census/non-BLADE datasets. The single largest re-validation risk is that NO committed script regenerates generated-schema-register.csv itself — it was produced by an ad-hoc live sampling run (including a one-off PIT run under /tmp/fplida-pit-schema/fplida_12k) — so progress cannot be measured automatically until that builder is reconstructed. The framework also surfaces concrete cross-domain inconsistencies in shared code frames (STATE, country-of-birth, ANZSCO, visa subclass) that a reimplementation must unify.

**Findings:**
- **Two-tier support verdict: scope/concept well-supported, exact codes underspecified** — full-review.md and source-gap-register.csv consistently grade datasets at the CONCEPT level (well-supported) but flag VALUE-DOMAIN level (underspecified). Census and BLADE are the strongest: Census has the ABS 2021 Census Dictionary as an authoritative per-variable source (graded 'Partly supported'), and all 825 generated BLADE variables match local inst/blade_metadata/variables.csv (direct_blade_variable_metadata). STP and PIT are 'Partly supported' because local PLIDA/DIL metadata proves the column names (all 92 STP rows direct-matched). Every other guide is graded 'Incomplete': Home Affairs, DHDA/Health, DSS, Education, VET/Apprentice, NDIS, Vital events, Core/Combined.
  - _Implication:_ Reimplementation should treat Census mnemonics and BLADE/STP/PIT DIL column names as fixed targets to match exactly, but must NOT invent category code values, frequencies, or distributions for the 'Incomplete' guides. Prioritise fidelity effort where official anchors exist (Census Dictionary, PBS API data dictionary, AVETMISS element definitions, TCSI elements E329/E330, AEDC 2025 dictionary, NACDC May 2026 table specs); keep everything else labelled local/synthetic.
- **Explicitly NOT source-equivalent fields must stay flagged** — crosswalk and full-review.md isolate the hard blockers. Four crosswalk-status rows are not source-equivalent: PIT_PS/SUPER_GUARANTEE (local SG logic, not RPRTBL_EMPLYR_SUPER_CNTRBN_AMT), PIT_PS/UNION_FEES and PIT_PS/WORKPLACE_GIVING (ATO concepts exist but no same-dataset PIT_PS metadata candidate), and NACDC/INDIGENOUS_STATUS (local Y/N collapse vs multi-category source). The stricter dhda-health-variable-code-evidence.csv adds NACDC COUNTRY_OF_BIRTH, MARITAL_STATUS, CARE_TYPE, HCP_LEVEL as concept-only, and flags NACDC STATE as needing a crosswalk change from RECIPIENT_STATE abbreviations to an ASGS STE_CODE-style field.
  - _Implication:_ These specific fields are landmines: a reimplementation that 'cleans them up' by inventing plausible source codes would regress the audit. They must remain labelled implementation-only until a same-dataset DIL source variable is found, and the re-validation step must assert their status is unchanged.
- **No committed builder for generated-schema-register.csv — the measurement baseline cannot be auto-reproduced** — The only register-building script in the repo is build-variable-code-evidence-registers.R, which CONSUMES the per-guide schema-registers/*.csv (joined to generated-variable-crosswalk.csv) to emit the five home-affairs/dss/education/vet-apprentice/ndis variable-code-evidence CSVs. There is no script that produces generated-schema-register.csv, generated-variable-crosswalk.csv, or local-metadata-variable-inventory.csv. generated-schema-register.qmd states the rows were sampled from live generated output, and PIT rows specifically came from a one-off targeted FY2021 run under /tmp/fplida-pit-schema/fplida_12k (5,990 PIT_PS / 5,223 PIT_ITR per sub-table / 6,055 PIT_IE rows). The .qmd files all have execute: eval:false, so they only render pre-built CSVs.
  - _Implication:_ Before measuring reimplementation progress, the schema-register builder must be reconstructed and committed: a script that (a) builds a fixed-size synthetic dataset with a fixed seed, (b) reads every emitted parquet, (c) for each column records type/n_rows/missing/missing_pct/distinct and either categorical top-values or numeric quantiles (min/p25/median/p75/max) or date range, and (d) left-joins to local PLIDA metadata (by dataset+variable) and BLADE metadata (by variable). PIT must be forced non-empty (the FY2021 targeted run). Without this, 're-validate the schema register' is a manual step and progress is unmeasurable.
- **Re-validation workflow: diff the regenerated register against the committed baseline** — The register schema is stable and diffable: generated-schema-register.csv keys on guide+dataset+table+variable with observed type/missingness/distinct/domain columns; generated-variable-crosswalk.csv keys identically and carries crosswalk_status (direct_blade_variable_metadata 825, direct_plida_dataset_variable 692, manual_same_dataset_plida_concept_match 58, generated_compact 4, generated_derived 2, external_source_concept_not_source_equivalent 3, local_generator_not_source_equivalent 1); local-metadata-variable-inventory.csv carries observed_in_generated_register (TRUE 24,242 / FALSE 25,745) which measures DIL coverage. The 38-row source-gap-register.csv is the human-readable guide-level scorecard.
  - _Implication:_ Re-validation is a three-part diff after reimplementation: (1) regenerate generated-schema-register.csv with the new builder and diff variable sets per guide to confirm no variables were dropped/renamed and counts hold (expect 1,585 unless coverage expands); (2) re-run build-variable-code-evidence-registers.R and confirm the not-source-equivalent rows are unchanged; (3) recompute observed_in_generated_register in the inventory to show coverage gains (e.g. education 216/2322, ndis 131/2647, pit 914/9018 metadata-row matches today). Progress = more variables matched, fewer 'not_found_or_not_proven' rows, and zero new fields that present synthetic distributions as source facts.
- **STATE code frame is inconsistent across datasets** — Most datasets emit state as ASGS numeric 1-8 (observed domain '1/1/2/3/8'): CORE STATE, AIR/MCD/DEX/NDIS/STP/A&T STATE_ASGS_2021, AEDC STATE, HE CAMPUS_STATE, MT_DEMOGS STATE_ASGS_2021, census STEUCD/STEUCP, BIRTHS/DEATHS REG_STATE, TVA HEAD_OFFICE_STATE/STATE_OF_FUNDING_GF/CLIENT_STATE_RESIDENCE_DERIVED. But DOMINO STATE and NACDC STATE emit abbreviations (NSW=489; VIC=327; QLD=302; ...). DEATHS REG_STATE is stored as a float (1.00/2.00/8.00). NDIS STATE_ASGS_2021 only spans 1-4 (sampling artifact or restricted domain). full-review.md and dhda-health-variable-code-evidence.csv already flag that NACDC STATE must move from RECIPIENT_STATE abbreviations to an ASGS STE_CODE-style field.
  - _Implication:_ The reimplementation must define one canonical state representation (ASGS STE_CODE 1-8 as the documented standard) and route every dataset through it, with abbreviation labels only as a derived display column where the real source uses them. A cross-dataset consistency test should assert STATE/STATE_ASGS_2021/REG_STATE share the same code domain and the same individual maps to the same state across Census, CORE, health, DSS, education, STP, vital events. DEATHS REG_STATE should be integer not float.
- **Country-of-birth frame conflates a SACC code with a born-in-Australia binary** — Two incompatible semantics share confusingly similar names. SACC-style country codes (1101 = Australia) are emitted by Census BPLP, CORE BIRTH_CTRY_CODE, DOMINO CTRY_CODE, HE COUNTRY_BIRTH (all character, top value 1101). But a column literally named COUNTRY_OF_BIRTH is emitted as an integer 0/1 binary (born-in-Australia flag) by NACDC, DEX, and A&T; and DOMINO BIRTH_CTRY_CODE is ALSO a 0/1 integer while DOMINO CTRY_CODE is the real 1101 code. SDB COUNTRY_OF_BIRTH is integer with domain all-1 in the sample.
  - _Implication:_ This is a naming-and-semantics trap: a variable named COUNTRY_OF_BIRTH that holds a 0/1 flag will silently corrupt any cross-dataset join or pooled analysis on country of birth. The reimplementation must (a) reserve *_CTRY_CODE / country-of-birth names for the SACC code frame and rename the binary fields to something like BORN_IN_AUSTRALIA_FLAG, and (b) ensure the same individual's country of birth is consistent across Census, CORE, DOMINO, HE, SDB. The audit should treat any 0/1 field named COUNTRY_OF_BIRTH as a defect to fix.
- **ANZSCO/occupation and visa-subclass frames are not unified** — Occupation: SDB OCCUPATION, A&T ANZSCO, and TVA ANZSCO_ID all emit full 6-digit ANZSCO unit codes (e.g. 621311, 561113) — but with a '0' sentinel for unknown in SDB/A&T. Census OCCP instead emits major-group-padded codes (100000/200000/300000) with '@@@@@@' as the ABS not-applicable symbol. So the same occupational concept appears at different ANZSCO levels with different missing-value conventions. Visa subclass: SDB VISA_SUB_CLASS is a single integer (100/189/190/...), while the VISA product splits it into VISA_SUBCLASS_CD (integer) + VISA_SUBCLASS_DS (character label) + VISA_PRGRM_DS/VISA_REPORT_GROUP_DS (program labels). source-gap-register.csv records that no public Home Affairs codebook was found proving the subclass values or labels.
  - _Implication:_ Reimplementation needs one canonical ANZSCO frame (full 6-digit unit codes, with consistent NA handling — distinguish ABS '@'/'&' supplementary symbols from a generated 0 sentinel) and a single visa-subclass code list shared between SDB and VISA so a person's visa subclass and its label agree across products. Because no public visa codebook was found, the subclass list and labels must stay labelled local/synthetic, but they should at least be internally consistent across the two Home Affairs products.
- **Full DIL surface vastly exceeds current generated output — coverage is the headline gap** — local-metadata-variable-inventory.csv has 49,987 metadata rows (44,729 PLIDA + 5,246 BLADE + 12 BLADE-key). The largest DIL datasets by metadata-variable rows are PIT_ITR 8,232, PBS 6,780, MBS 6,408, BLADE 5,246, STP 5,208, CORE 3,871, NDIS 2,647, AEDC 2,253, TVA 2,007, DEATHS 1,711. Generated output covers only a slice: the schema register has 1,585 generated variable rows total, and full-review.md P0 explicitly warns against conflating the full PLIDA surface with the compact generated output. NDIS in particular emits only 11 generated variables against a 2,647-row metadata surface.
  - _Implication:_ The plan should set explicit coverage targets per guide rather than aiming for full DIL parity. Use observed_in_generated_register as the running coverage metric. Datasets with the widest gap between concept support and generated coverage (NDIS 11 vars, PIT vs 8,232 PIT_ITR metadata rows, AEDC, MBS/PBS compact vs 6,000+ metadata rows) are where added fidelity buys the most, but each new variable must come with a source anchor or stay labelled synthetic.

**Recommendations:**
- Reconstruct and commit a deterministic builder for generated-schema-register.csv before measuring any reimplementation progress. It should build a fixed-seed synthetic dataset, read every emitted parquet, record per-column type/n_rows/missing/missing_pct/distinct + categorical top-values or numeric quantiles or date range, and left-join local PLIDA metadata (dataset+variable) and BLADE metadata (variable). Force a non-empty PIT FY2021 run (the existing /tmp/fplida-pit-schema/fplida_12k pattern). Without this, the entire reconciliation framework is a static snapshot that cannot be refreshed.
- Make re-validation a committed diff pipeline: after reimplementation, regenerate the schema register and crosswalk, then assert (a) per-guide variable sets and the 1,585 total are preserved or grown, (b) crosswalk_status counts hold and the 4 explicitly not-source-equivalent rows (PIT_PS SUPER_GUARANTEE/UNION_FEES/WORKPLACE_GIVING, NACDC INDIGENOUS_STATUS) plus the dhda-health value-domain flags are unchanged, and (c) observed_in_generated_register coverage in the 49,987-row inventory is non-decreasing. Re-run build-variable-code-evidence-registers.R as part of the same pipeline.
- Treat the source-gap-register.qmd Use Rule as a hard constraint on the reimplementation: do not promote any sampled generated value, category label, distribution, or cutoff to a source-backed fact. Where the 38-row source-gap-register.csv says 'not found or not proven' (e.g. visa/traveller codebooks, DOMINO variable-level pages, HE TCSI mappings, AEDC cutoffs, apprentice qualification weights, BIRTHS/DEATHS distribution targets), keep the field labelled local/synthetic and do not invent detail to close the gap.
- Introduce a canonical-code-frame module shared across all generators and add cross-dataset consistency tests for the four frames the registers expose as inconsistent: STATE (standardise on ASGS STE_CODE 1-8 numeric, abbreviations only as derived labels; fix DOMINO/NACDC abbreviations, DEATHS float, NDIS 1-4 truncation), country of birth (reserve SACC code frame for *_CTRY_CODE names and rename the 0/1 fields to BORN_IN_AUSTRALIA_FLAG so NACDC/DEX/A&T/DOMINO-BIRTH_CTRY_CODE stop colliding with the real code), ANZSCO (one 6-digit unit-code frame with consistent NA handling distinct from ABS '@'/'&' symbols), and visa subclass (one shared subclass code+label list across SDB and VISA). Tests should assert the same individual resolves to the same state, country of birth, and occupation across datasets.
- Prioritise fidelity work by where official anchors already exist and coverage is thin: Census (ABS Dictionary, authoritative), PBS (PBS API data dictionary), VET/TVA (AVETMISS element definitions — including tightening state codes to two-character 01-08/09/99), HE attendance type/mode (TCSI E330/E329), AEDC (2025 dictionary — but verify the 4.5/6.0 vulnerability cutoffs against official scoring rules before promoting them), and NACDC (May 2026 table specifications). Use the per-guide schema-registers/*.csv and the seven variable-code-evidence registers as the controlling source-status layer for build tests, exactly as full-review.md 'Required next work' item 4 directs.
- Keep the four-layer separation intact in any reimplementation docs: metadata inventory (DIL surface) vs current generated output (schema register) vs official/public dictionary coverage (source-gap + evidence registers) vs unresolved gaps. full-review.md P0 flags that conflating these is the recurring failure mode; the reimplementation should preserve the distinction rather than merging them into a single 'data dictionary' that reads as if generated values are source facts.

**Current state:** All three PIT generators are fully Rust-first with thin R facades, and each compact column the explainer documents is present, correctly named, and matches its documented domain in the FY2021 sampled build (44 of 58 variable rows are direct local-PLIDA name matches; the rest are documented manual crosswalks or intentionally not-source-equivalent fields). The PIT_PS occupation-noise model, archetype-keyed deduction medians, simplified progressive tax/LITO/Medicare schedule, and income-banded filing-probability model are all implemented as the explainer describes and the foundation TOMLs calibrate. The generation is deliberately compact (not DIL-shaped): PIT_PS emits 14 of ~40 DIL items, PIT_ITR emits ~23 of 601 DIL items, and the explainer explicitly instructs that omitted DIL items must NOT be treated as gaps. The principal real defects are (a) PIT_IE is produced in total isolation from PS/ITR so the three products do not reconcile at person-year level, (b) several distribution parameters are hard-coded in pit_ie.rs with no TOML and look mis-specified, and (c) a handful of naming/range issues (FY type mismatch across products, SG vs reportable-employer-super mislabel, INCM_YR stored as integer end-year).

**Authoritative spec:** The explainer defines PIT_PS as employer-reported annual payment-summary rows at person-employer-year level (gross, tax withheld, reportable FBT, reportable employer super, lump sums A/B/D/E, allowances, foreign-employment income, period dates); PIT_ITR as lodged returns where non-lodgers are absent (salary/wages closely tracking aggregated PS gross with small discrepancy noise, plus business/interest income, deductions, a simplified progressive-tax/LITO/Medicare-levy calculation, and a balance equal to net tax less aggregated PS withholding); and PIT_IE as ABS-derived income built FROM PS and ITR to align with ABS income concepts, with component earner flags 'E'/'N' iff the component is non-zero and NONLODGER recording whether the wages source was the tax return ('ITR') or payment summary ('PS'). The research's required semantic relationships (explainer 'Validation checks', lines 562-607) are explicit: ITR salary/wages must be highly correlated with aggregated PS gross but not exactly equal; ITR filers must be a subset of person-years with PS records; BAL_PYBLE_RFNDBL_AMT must equal NET_TAX_AMT less aggregated PS tax withheld; PIT_IE TOTALINC must equal the component sum before editing noise; earner flags must be 'E' iff component non-zero; NONLODGER must use only 'ITR'/'PS'. The explainer repeatedly states the compact schema is intentional and that omitted DIL items (dividends, foreign income, HELP/SSL repayments, Medicare levy surcharge, private health rebate, spouse/family income tests, period dates) are out of scope by design, not gaps. It flags as known caveats: SUPER_GUARANTEE is local SG logic not the DIL reportable-employer-super concept; UNION_FEES and WORKPLACE_GIVING have no same-dataset PIT_PS metadata; PIT_PS lacks period dates so it cannot reproduce ABS divisor methods; and PIT_IE's editing-noise model and component distributions are not source-validated.

## BLADE business module (ABS Business Longitudinal Analysis Data Environment)

**Generators:**
- `BLADE business spine + 62 DIL tables + key products` — R: R/generate_blade.R; Rust: src/rust/src/business_pool.rs; TOML: inst/foundations/blade.toml
  - emits today: Business spine (_system/business-spine.parquet, ~90 cols), PLIDA-BLADE link (_system/plida-blade-link.parquet), all 62 blade-table-NN-* products, and the two Appendix key products (blade-key-id-to-bn-key, blade-key-cn-to-bn-key).

**Current state:** BLADE is generated almost entirely in R: generate_blade.R is 2,372 lines and does all spine construction, person-business linkage, and per-table value generation through a generic name/Valid.Response pattern-matcher (.blade_value_for and its table-specific helpers .blade_bas_value_for, .blade_bit_value_for, .blade_stp_value_for, .blade_bcs_value_for, .blade_metadata_value_for). The only Rust is business_pool.rs (102 lines), a process-global Vec<String> of `bn` values that PIT_PS and STP draw from so employer identifiers resolve to real BLADE businesses; it does no table generation. The generated schema is faithful at the column-name level (the evidence appendix reports 825/825 generated variables as Direct local BLADE metadata matches across tables 1, 4, 5, 6, 7, 17, 27 in the sampled build), and several relationships are deliberately and correctly modelled (BAS amount inequalities, PAYG hcnt vs linked-person gaps, ANZSIC Division Q health businesses, mixed-case join keys). But many categorical fields ignore the code frame the metadata itself carries, and a class of "Amount" fields is emitted as 0/1 integers or year values rather than dollars.

**Authoritative spec:** The April 2026 BLADE Modular Product DIL defines 62 tables (1-34 standard, 35-62 requestable) plus two Appendix key products, with per-variable Valid.Response code frames in inst/blade_metadata/variables.csv and keys.csv. Identifiers (bn, id, bg_id, cn) are 10-digit alphanumeric and are local synthetic identifiers that the research says to preserve. The keys.csv specifies exact code frames the generator must honour: `match` takes {One-TAU-BG, Class, Group, SubDiv, Div, BG Match, NPP}; one_abn_to_many_tau and many_abn_to_one_tau take {1=Yes, 0=No, .=Missing}. Table 17 (EEH) coded fields have explicit frames: payfreq_eeh {1=Weekly,...}, rop_eeh {1=Adult rate,...}, agecat_eeh {1=Under 18 years,...}, mosp_eeh {1=Award only,...}, ftpt_eeh {1=Full-time, 2=Part-time}, typeemp_eeh {0=Not applicable (owner-manager), ...}, casload_eeh {0=Not applicable,...}, stateops_eeh {1=All states selected}, sex_eeh {1,2}, state_eeh {1=NSW,...,8}. Table 7 (STP) ed_* fields are all "Numeric response ($)" dollar amounts; month_actioned is "3 Character Mmm" (Jan/Feb/...); branch_number is "Numeric response". Table 6 (BIT) carries real code frames such as c_agrgtd_tnovr_rng_cd {5,10,...,80 = turnover bands} and c_base_rt_bus_cd {5=Base rate entity}, alongside many "Numeric response ($)" amount fields including year-named amounts (c_erlyst_yr_it_lblty_amt, c_esi_to_prvs_yr_amt). The research treats local Valid.Response as the categorical source of truth and warns ABS public pages do not give full distributions, so distributions are implementation choices but code frames are authoritative.
